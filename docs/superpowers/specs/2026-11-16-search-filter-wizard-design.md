# Search Filter Wizard — дизайн

## Намерение

При первом открытии приложения пользователь не должен разбираться в каталоге и
навигации. Основной экран сразу запускает короткий диалог, собирающий параметры
поиска. Любой вопрос и весь опрос можно пропустить. После завершения ответы
сохраняются в PostgreSQL и используются для подбора организаций; в будущем эти
записи станут источником продуктовой аналитики.

## Цели

- мобильный сценарий, которым удобно пользоваться одной рукой;
- один вопрос на экран без визуального шума;
- отсутствие обязательной регистрации и обязательных ответов;
- одна запись фильтра на один завершённый или полностью пропущенный опрос;
- рекомендации используют заполненные поля, а не только сохраняют их;
- сохранение Clean Architecture, CQRS, отдельных repository и Unit of Work;
- исправление найденных проблем JWT refresh, гонок загрузки, модальных окон и
  перегруженных frontend-компонентов.

## Не входит в задачу

- отдельная аналитическая панель;
- геолокация устройства;
- NLP/семантический поиск по пожеланиям;
- редактирование старых фильтров;
- обязательная авторизация перед поиском.

## Выбранный подход

Выбран вариант архитектурной стабилизации с сохранением общего визуального
характера приложения, но с более минимальным первым экраном.

Рассматривались:

1. Только CSS-адаптация текущей страницы — быстрее, но не устраняет перегруженные
   компоненты, ошибки сессии и отсутствие аналитической сущности.
2. Полная замена frontend и навигации — дороже и несёт лишний риск регрессий.
3. Пошаговый wizard плюс целевой рефакторинг — выбран: меняет главный сценарий,
   но сохраняет рабочие каталоги, кабинет и API-контракты там, где они подходят.

## Пользовательский сценарий

Wizard показывается сразу при каждом новом посещении главного экрана:

1. **Что хотите посетить?** Выбор типа организации крупными карточками.
2. **Какой общий бюджет?** Числовое поле и быстрые варианты суммы.
3. **Сколько человек?** Крупный stepper/варианты; значение влияет на расчёт.
4. **В каком городе?** Текстовое поле с подсказками из существующих организаций.
5. **Есть дополнительные пожелания?** Свободный текст до 500 символов.

На каждом шаге доступны «Пропустить» и «Назад» (кроме первого). Постоянно видна
кнопка «Пропустить всё». Ответ сразу переводит к следующему вопросу; для
текстовых и числовых полей переход выполняется кнопкой «Продолжить» или Enter.
Прогресс показывается точками и текстом «N из 5».

После последнего ответа или «Пропустить всё» frontend один раз отправляет фильтр,
получает сохранённую сущность и рекомендации. Если бюджет пропущен, показываются
подходящие организации без обещания попадания в сумму. Если заполнены пожелания,
на первой версии они участвуют в простом регистронезависимом поиске по названию и
описаниям организации и позиции.

## Доменная модель

`RecommendationFilter`:

- `id: UUID`;
- `user_id: UUID | None` — заполняется для авторизованного пользователя;
- `client_id: UUID` — анонимный стабильный идентификатор браузера, генерируется
  frontend и не содержит персональных данных;
- `organization_type_id: UUID | None`;
- `budget: Decimal | None`, неотрицательное значение;
- `party_size: int | None`, диапазон 1–20;
- `city: str | None`, нормализованная строка до 120 символов;
- `wishes: str | None`, строка до 500 символов;
- `currency: str`, по умолчанию `RUB`;
- `created_at: datetime`.

`NULL` означает пропущенный вопрос. Отдельный массив пропусков не хранится: он
дублировал бы состояние полей. Индексы создаются по `created_at`, `user_id`,
`client_id`, `organization_type_id` и `city` для будущей аналитики.

## Backend

- отдельные domain entity, repository port и SQLAlchemy repository;
- отдельная ORM-модель и новая Alembic-миграция;
- Unit of Work получает `recommendation_filters`;
- CQRS-модули:
  - `CreateRecommendationFilterHandler`;
  - `ListUserRecommendationFiltersHandler`;
  - существующий query рекомендаций расширяется nullable-бюджетом и пожеланиями;
- `POST /api/v1/recommendation-searches` принимает ответы, сохраняет фильтр и
  возвращает `{filter, recommendations}` в одной транзакции;
- `GET /api/v1/recommendation-filters/me` возвращает историю текущего пользователя;
- авторизация POST-поиска необязательна: отдельная optional-user dependency
  извлекает пользователя при наличии корректного access JWT;
- лимиты и нормализация проверяются в domain/application, а Pydantic повторяет
  внешние ограничения для ранней ошибки API.

## Frontend-архитектура

- `App` отвечает только за маршрутизацию верхнего уровня и состояние сессии;
- `SearchWizard` управляет шагами и черновиком фильтра;
- каждый сложный шаг — небольшой самостоятельный компонент;
- `ResultsView`, `PlaceModal`, `AppHeader` и `MobileNavigation` отделяются;
- `useSession` управляет восстановлением пользователя и refresh-token;
- `usePlaceDetails` отменяет устаревшие запросы и исключает гонки;
- API client обновляет access token для `/auth/me`, но не зацикливает refresh;
- `client_id` хранится в localStorage, черновик wizard — в sessionStorage;
- ошибки поиска, каталога и авторизации имеют раздельное состояние.

## Мобильный дизайн

- фон тёплый молочный, основной цвет глубокий хвойный, акцент приглушённый лайм;
- минимум декоративных блоков, один главный вопрос и много свободного пространства;
- размер интерактивной зоны не меньше 44×44 px;
- основные кнопки закрепляются над `env(safe-area-inset-bottom)`;
- поля имеют минимум 16 px шрифт, чтобы iOS не увеличивал страницу;
- wizard занимает `100dvh`, клавиатура не перекрывает активное поле;
- после wizard нижняя навигация не перекрывает контент на телефонах и планшетах;
- модальные окна закрываются по Escape, блокируют фон и используют bottom-sheet на
  узких экранах;
- поддерживаются `prefers-reduced-motion`, focus-visible и aria-атрибуты.

## Тестирование

- backend unit-тесты валидации и создания фильтра;
- repository-тест сохранения nullable-полей;
- API flow для анонимного и авторизованного поиска, включая историю пользователя;
- тест refresh `/auth/me` на frontend API client;
- компонентные тесты wizard: переход, пропуск шага, «Пропустить всё», один submit;
- проверки viewport 320, 375, 768 и desktop: отсутствие горизонтального overflow,
  доступность кнопок при экранной клавиатуре и safe-area;
- полный Ruff, Mypy, Pytest, ESLint, TypeScript build и frontend test suite.

## Ошибки и крайние случаи

- повторный клик не создаёт две записи: submit блокируется до ответа;
- неизвестный тип организации возвращает 404/422 без частичной записи;
- пустые строки нормализуются в `NULL`;
- истёкший access token обновляется перед `/auth/me`;
- ошибка API не уничтожает черновик, пользователь может повторить отправку;
- поздний ответ отменённого запроса не заменяет данные открытой организации.
